# Distilaide Mandates

## Current state

Image restoration — **image → image** — on **ALL EIGHT** engines, driven by ONE config: standard
PyTorch Lightning, a hand-written torch loop, a fastai `Learner`, Keras 3, a native TensorFlow
`tf.data` + `GradientTape` loop, a jitted JAX/optax loop, Apple's MLX, and a `transformers.Trainer`
over Swin2SR. `cli.FRAMEWORKS` is COMPLETE: every backend it advertises is real. The canonical task
is **Gaussian denoising**, the textbook image-to-image problem — DnCNN, DRUNet and SCUNet were all
trained by adding synthetic noise to clean photographs, because the clean image is the only ground
truth that exists (a real noisy photograph has no noise-free twin).

Modules: `lightning_restorer.py` / `torch_restorer.py` / `fastai_restorer.py` / `keras_restorer.py`
/ `tensorflow_restorer.py` / `jax_restorer.py` / `mlx_restorer.py` / `huggingface_restorer.py` (the
merged train/evaluate/test/predict classes), the ZOO WRAPPERS `deepinv_model.py` (`DeepInvModel`
over `deepinv.models` — FOURTEEN architectures from an `arch:` string, learned AND classical) and
`huggingface_model.py` (`HuggingFaceRestorationModel` over Swin2SR), the `dncnn/` PACKAGE (`spec.py`
+ `torch_dncnn.py` + `keras_dncnn.py` + `tensorflow_dncnn.py` + `flax_dncnn.py` + `mlx_dncnn.py` —
the shared architecture, written FIVE times and held together by a DERIVED parameter count of
**57,635**, which all five report including under custom `depth`/`width`), `torch_restoration.py` +
`keras_restoration.py` (registered upstream losses/metrics, ONE MODULE PER LOSS API), the spelling
shims `_keras.py` / `_tensorflow.py`, and `cli.py` (`distilaide train/evaluate/predict cfg.yaml
[--framework <name>]` + a `frameworks` listing command). Datasets are the generic
`recordstream.sources.huggingface.HuggingFaceSource`; batches are **record dicts** addressed by
configured keys (`input_key="image"` = the DEGRADED input / `target_key="target"` = the CLEAN ground
truth).

Example config: `examples/train_dncnn_denoising.yaml` — **it trains end to end on all eight
backends**, changing only the flag (Oxford-IIIT Pet, 256-row slice at 192x192, sigma 0.1, 5 epochs;
verified 2026-08-05/06). The number that matters is the one against the DO-NOTHING baseline, because
a restoration metric is never near zero — **the noisy input itself scores PSNR 20.53 dB / SSIM
0.3719 / MS-SSIM 0.8516** on the val split:

| backend | model | val PSNR |
|---|---|---|
| huggingface | Swin2SR (from scratch) | **27.41 dB** |
| fastai | deepinv DnCNN (668K) | 24.4–25.2 |
| torch | deepinv DnCNN (668K) | 22.2–22.9 |
| lightning | deepinv DnCNN (668K) | 21.5–22.5 |
| jax | FlaxDnCNN (the 57K spec) | 20.56 |
| tensorflow | TensorFlowDnCNN (spec) | 20.49 |
| keras | KerasDnCNN (spec) | 20.38 |
| mlx | MlxDnCNN (spec) | 20.31 |

**Read that table by GROUP, not by rank — the model differs, and that is the design.** The four
spec backends agree within 0.25 dB, which is what the shared spec EXISTS to demonstrate (same
network, five frameworks); the zoo backends do better because a 668K DnCNN beats a 57K one, measured
directly on one loop (`TorchDnCNN` 20.74 dB against `DeepInvModel(arch=dncnn)` 21.47 dB, same data,
same epochs); and Swin2SR wins because a transformer with a `Trainer`'s schedule beats both.
Those figures predate the seeding and are RANGES for that reason; the config is seeded now (mandate
below) and a repeat run reproduces exactly.

The check worth keeping is the other end: the FIRST-EPOCH score (20.45–20.58 dB) matches the
baseline to within 0.1 dB, so a first epoch far from the floor means the PAIR is wrong rather than
the model being good. **The mechanism is TRAINING, not initialization, and the tempting explanation
is measurably false:** predicting zero noise is a residual denoiser's cheapest local optimum and it
gets there within one pass — but AT INIT it is nowhere near the identity (measured on `[0, 1]`
images: `TorchDnCNN` deviates by mean 0.35 / max 1.86, deepinv's own DnCNN by mean 0.24 / max 1.08,
because both initialize the final convolution the usual way rather than at zero).

**A BACKEND SWEEP (`examples/sweep/`, 2026-08-06) is what turns that table into a comparison** — eleven cells over one config, the three torch backends trained TWICE (zoo and shared spec) so a column compares FRAMEWORKS rather than networks. Its own verified numbers are in the sweep mandate below; the two worth carrying here are that a `pl.Trainer` and a hand-written loop land **0.017 dB apart** on the same config (20.7055 / 20.7222), and that the five `*DnCNN` implementations span **under half a dB** (20.24-20.72). It found THREE real bugs on its first run, all of which were invisible while each backend was read alone.

**The 2026-08-05 rebuild replaced everything.** `distilaide/api.py` (the `denoise(signal,
method=...)` dispatcher), `bm3d_backend.py`, `noisereduce_backend.py`, `deepinv_backend.py` and
`asteroid_backend.py` are DELETED with no back-compat aliases, along with the `list-methods` /

(asteroid, noisereduce — speech enhancement and spectral gating) is gone entirely: it was a second,
unrelated identity in a project whose subject is images. The IMAGE methods SURVIVE, promoted rather
than removed — `bm3d`, `dncnn`, `drunet`, `swinir`, `scunet`, `restormer` are all `arch:` values of

- **The Lightning Backend Is Built On The WORKSPACE TRAINER BASES (`RestorationBase` + `RestorationTorchHooks` + `matrainer.lightning.LightningRunnable`, 2026-08-06):** the trainer machinery moved UP to matrainer (a user-authorized reversal of its tracking-only rule — matrainer `AGENTS.md` + its `docs/architecture.md` record 9): `matrainer.runnable.TrainerRunnable` defines the neutral API (slots, `run()` dispatch, the four `@entrypoint`-marked capabilities, tracker/prepare/prediction plumbing), `matrainer.torch.runnable.TorchTrainerRunnable` pins the torch types (`model: Partial[nn.Module]`, the `MetricsSpec` quartet, the metric builders, the sidecar write, `trained_model`), and `LightningRunnable` fills in the Lightning machinery (loaders via `recordstream.loaders.loader_slots`, the deferred `pl.Trainer` slot + `_build_trainer` tracking hookup, the step functions, the entrypoints). THIS project owns the TASK half, written ONCE for the whole engine fleet: `restoration_base.py` (torch-free — the keras/jax/mlx backends import it too) + `restoration_torch.py` (the torch-typed hook implementations; NOT to be confused with the loss/metric REGISTRATION module). ``LightningRestorer`` is now `(`RestorationTorchHooks`, LightningRunnable)` + its own FULL flat `__init__` (the confluid introspection surface — signature unchanged, so configs/schemas/TASK_REGISTRY are untouched). Consequences to know: the old "removing matrainer keeps it training" claim is DEAD BY DESIGN (matrainer is now load-bearing for training); the fleet drift tests carry a shared-base exemption (a module built on `LightningRunnable` must NOT shadow `_build_trainer`/`_live_trackers`/`_run_eval`/`_report_epoch_metrics` — the inherited wiring is pinned in matrainer's own suite); confluid's body-slot scans see the inherited slots because the bases are `@configurable(validate=False)` (the `Tracker`-ABC precedent — do not remove the mark, it is what keeps `optimizer:`/`loss_fn:`/loader keys in every form-spec). **The bare-torch backend JOINED the shared bases on 2026-08-07 (P2):** ``TorchRestorer`` is now `(RestorationTorchHooks, matrainer.torch.TorchLoopRunnable)` — the owned-loop machinery (the epoch driver, device bracketing via `resolve_device`, `_score`, the plain-`state_dict` checkpoint, the plain-function tracking hookup incl. the per-epoch `tracker.log_metrics` and the terminal `capture_log_file`) lives in `matrainer/torch/loop.py`, and the concrete is CTOR-ONLY: the full flat signature (unchanged) plus the one stored task knob, `data_range`. The fleet exemptions key on EITHER machinery base (`LightningRunnable` OR `TorchLoopRunnable` in the source) and forbid shadowing the loop wiring (`fit`/`_score`/`_epoch_metrics`/`_log_run_context`) exactly as they forbid the Lightning names.  **The fastai backend JOINED on 2026-08-07 (P3):** ``FastaiRestorer`` is now `(RestorationTorchHooks, matrainer.fastai.FastaiRunnable)` — the Learner machinery lives in `matrainer/fastai/learner.py`, and the concrete keeps its FULL flat ctor (signature unchanged, `data_range` included) plus the task's fastai VOCABULARY as hooks: `_default_fastai_metrics` (mse/mae — fastai ships no PSNR/SSIM) and `_metric_aliases` (`psnr` → the `PeakSignalNoiseRatio` accumulator, still in this module; the default loss falls through to the task hook's L1). Its `evaluate` now scores the VAL split (it used to delegate to `test()`). The OTHER five backends still carry their private copies — the migration roadmap is phased by framework family (root `TASKS.md`).
- **Denoising Is A PAIR You MAKE, Not A Dataset You FIND — The Degradation Lives In The CONFIG (2026-08-05):** there is no paired noisy/clean dataset here and that is a decision, not a gap. It was searched for first: the HF hub has no small, properly-paired image→image set that `HuggingFaceSource` can load — `huggan/facades` and `huggan/maps` ship their pairs as raw byte structs rather than `Image` features, `eugenesiow/Div2k`'s `lr`/`hr` columns are STRINGS (script-based, dead under `datasets` 5.x), `geekyrakshit/LoL-Dataset` and `Jason0411202/USenhance2023_Aligned` separate their pairs by a `ClassLabel` instead of pairing per row, `deepinv/drunet_dataset` is 5 GB and `deepinv/denoising` is 6 rows — and recordstream has NO pairing source (`sources/` = base/concat/huggingface/range/split), so stitching two repos is not available either. So the target is DERIVED, in three ops that needed NO new primitive: `ConvertToImage` (resize) → `CopyField(src=image, dst=target)` (the clean copy) → `albumentations.GaussNoise` (degrade the input alone). **The consequence is that the DATASET is interchangeable and the DEGRADATION is the task** — Oxford-IIIT Pet is used because it is natural photography, small, and already cached in this workspace, not because it is a denoising set. **`deepinv/CBSD68`** (68 rows, 20 MB, a real `Image` column) is the canonical colour-denoising BENCHMARK and is the right `test_set` for a published number. **ORDERING IS LOAD-BEARING and silent when wrong:** a bare albumentations transform receives only albumentations' OWN key vocabulary (`_ALB_KEYS` = image/mask/masks/bboxes/keypoints/labels), so a `target` key is invisible to it — everything that must reach BOTH halves goes ABOVE the copy and everything that degrades the input goes BELOW it. A resize placed after the copy moves the input and leaves the target at its original size, unpairing every record while still producing a perfectly valid-looking batch (pinned, with the counterfactual EXECUTED, by `tests/test_examples_load.py::test_a_resize_after_the_copy_would_unpair_the_record`). Both halves also need their own `ToTensor(normalize=True)`: a normalized input against a uint8 target is a loss that never converges and never says why.
- **`data_range` Is This Task's `num_classes`, And Getting It Wrong Is SILENT (2026-08-05):** every full-reference image metric is defined relative to the span of the target's values, so the restorer takes `data_range: float = 1.0` and injects it into every metric template exactly as a per-pixel task injects `num_classes`. **Measured on one batch of `[0, 1]` images: PSNR reports 20.46 dB at `data_range=1.0` and 68.59 dB at `255.0` — the same tensors, scored as if the model were near-perfect.** torchmetrics 1.9 makes `data_range` a REQUIRED argument of `PeakSignalNoiseRatio` (no default) for exactly this reason, which is why a metric must be wired as a `!lazy:` TEMPLATE rather than an eager `!class:...()`: the template receives the run's value, while an instance would have to restate it and give the config two places to disagree about one scale. **It forced a matrainer fix in the same change, and that fix is the general rule:** `build_metric_collection(spec, **flow_dims)` used to flow EVERY template with EVERY dimension, which worked for classification by luck (every `torchmetrics.classification` metric happens to take `num_classes`). Only THREE of the seven full-reference image metrics take `data_range` — `PeakSignalNoiseRatio` plus the two SSIMs; `SpectralAngleMapper`, `UniversalImageQualityIndex`, `ErrorRelativeGlobalDimensionlessSynthesis` and `RootMeanSquaredErrorUsingSlidingWindow` do not — so wiring one of those four beside the defaults broke the WHOLE collection. `matrainer.torch.metrics._sizing_kwargs` now applies a dimension per template, filtered TWICE: the target must DECLARE the parameter, and must not have PINNED it already (which also makes the injection a FLOOR — a template writing its own `data_range: 2.0` keeps it, where a runtime kwarg would otherwise override). **The declaration check is `inspect.signature`, deliberately NOT `confluid.accepts_key`** — every torchmetrics metric takes `**kwargs` (the base `Metric.__init__` uses it for `compute_on_cpu`/`dist_sync_on_step`) and then REJECTS anything else, so `accepts_key` answers yes for all of them.
- **REPRODUCING A RUN TAKES TWO SEEDS, AND THE OBVIOUS ONE IS NOT ENOUGH (2026-08-06):** the sweep's whole value is that a row means something, which requires the row to be repeatable — and getting there needed BOTH a model seed and a degradation seed, measured on two runs of the identical `--framework torch` cell: unseeded **22.7530 / 22.5188** (0.234 dB), model-seeded **22.1058 / 22.1707** (0.065), model + degradation **22.1886 / 22.1886** (ZERO). **(1) `seed:` on a model wrapper calls `torch.manual_seed` at BUILD time and deliberately does NOT restore the previous state.** That leak is the mechanism rather than an oversight: the build happens once, before any training randomness is drawn, so seeding there is a run-level seed applied at the earliest useful moment — it fixes the loader's shuffle order as well as the weights. A save-and-restore version was written FIRST and measured (22.1891 / 21.9956, barely better than unseeded): it gives a reproducible MODEL inside a run that still is not reproducible, which is the shape of answer nobody wants. `DeepInvModel` and `HuggingFaceRestorationModel` gained the knob in that change; the five shared-spec implementations always had it, and it now means ONE thing across all seven wrappers. **A related trap for anyone reading the measurements: `torch_dncnn` was already bit-identical run to run, which looks like "the init is the whole variance" and is FALSE** — it reproduced because `TorchDnCNN.solidify` seeds the global RNG and does not restore it, so everything downstream was seeded too. **(2) The DEGRADATION needs its own seed and can only get one through a `Compose`.** A bare albumentations transform builds its RNG from OS entropy and REFUSES the argument (*"Argument(s) 'seed' are not valid for transform GaussNoise"*, measured), so every `preprocess` chain wraps its `GaussNoise` in a one-element `!class:albumentations.Compose {seed: 0}` — five chains in the example, one in the sweep overlay. Two FRESH seeded Composes draw identically while ONE called twice does not, which is exactly what a per-record stream needs and is what makes the RUN reproduce rather than every record getting the same noise. This matches recordstream's own note that seeding is the libraries' own mechanism (`A.Compose(seed=…)`). **What still is NOT seeded** is anything a config cannot reach: a second `Compose` in the chain would need its own `seed:`, and nothing here pins CUDA/MPS kernel determinism — CPU and MPS were BOTH measured non-reproducible before the degradation seed and both exact after, so kernel nondeterminism is not a factor at this size.
- **The Backend SWEEP Is An OVERLAY, And The MODEL Is A Second DIMENSION (`examples/sweep/`, 2026-08-06):** `run_sweep.sh` trains every INSTALLED backend into one tracker — the three torch ones TWICE, on the deepinv zoo wrapper and on the shared DnCNN spec — and `all_backends.yaml` is what it drives: an overlay that `include:`s `train_dncnn_denoising.yaml` and overrides only what a sweep needs (a `tracker` dimension, one metric vocabulary, and the two blocks whose output paths move under `sweep_logs/`). **ELEVEN cells, and both gaps are STRUCTURAL:** there is no non-torch restoration ZOO to wrap (deepinv is torch-only — the observation `dncnn/spec.py` exists to answer), and **`huggingface` takes no dncnn for a NARROWER reason than the per-pixel project's, which is the interesting part.** There, the gap is that a `transformers.Trainer` drives models computing their own loss from `labels=`; HERE that is not the obstacle at all, because this backend already ships a `Trainer` subclass applying `loss_fn` itself. What remains is purely the CALLING CONVENTION: `Trainer`'s EVALUATION path calls `model(**inputs)`, so a model must take `pixel_values=` and `labels=` as KEYWORDS, and `TorchDnCNN.forward(images)` does not — measured, it TRAINS fine and dies on the first eval with *"got an unexpected keyword argument 'pixel_values'"*. Teaching the shared spec transformers' keyword names would put one framework's convention inside the class whose whole job is to be the same network in five of them, so the cell stays out — and because the huggingface block is spliced AFTER the top-level `dncnn:` one, `--model dncnn` simply leaves that row alone, which makes the failure UNREACHABLE rather than merely undocumented (pinned). **The `!scope:model=dncnn` block lives in the EXAMPLE, not in the overlay** — making the shared spec reachable is worth having on a default checkout, and before it `TorchDnCNN` was wired NOWHERE outside its own unit test while its four siblings each trained. **THREE composition rules, all inherited from the sibling projects and all silent when wrong:** (1) a scope block REPLACES rather than merges (`include:` deep-merges MAPPINGS and a `!scope:` parses to a `ScopeBlock`), so an overlay block restating one key discards the runnable, the model and the preprocess chain with it — restate the whole block; (2) **a deep-merged key keeps its ORIGINAL POSITION**, so a key only the overlay introduces is appended at the END and beats any block the example already declares — which is why the fastai and huggingface metric lists are CONSTRUCTOR kwargs, immune to document order, rather than sibling keys the top-level `metrics:` mapping would overwrite; (3) the four non-torch blocks need NO nested `dncnn:` block, because each wires its implementation unconditionally and is spliced AFTER the example's top-level one (pinned, since that is a property of document ORDER an edit can reverse silently). **NO ROW PINS AN ENGINE, and that is a RESULT rather than an omission:** the per-pixel sibling must export `KERAS_BACKEND=tensorflow` on its keras row because `keras.metrics.MeanIoU` scatters per PIXEL on the torch engine; restoration's Keras metrics are `keras.ops.psnr` and a mean squared error — no scatter — so the keras row runs on whichever engine is bound, which is the whole point of that backend. **The `tensorflow` row DOES need the pin and the CLI now sets it itself, which is a BUG THIS SWEEP FOUND** — see the CLI mandate. **The shared columns are `psnr` + `mse` and SSIM is deliberately excluded**: `keras.ops` has no SSIM and the only implementations are engine-SPECIFIC, so it can never be more than a 2-of-11 column; MS-SSIM is dropped for the same reason plus cost. **What the sweep is FOR is the ragged column, so do not trim one away** — it found fastai unable to report PSNR at all (closed by the CONFIGURED ALIAS below), and it is what makes the two-group reading of the results table reproducible rather than hand-measured. `matrainer.sweep` holds the tracker-side halves AND, since 2026-08-07, the DRIVER (`matrainer sweep backends examples/sweep/sweep.yaml`, also `trackers`/`all` modes) — `run_sweep.sh` is DELETED and this project keeps only the declarative MATRIX, `examples/sweep/sweep.yaml` (11 cells, the `--model dncnn` variant, the probes, the mlflow `tracker_setup`), pinned against the test table by `tests/test_sweep_config.py::test_the_sweep_spec_declares_exactly_this_matrix`; each cell runs through the generic `matrainer train`. Pins: `tests/test_sweep_config.py` (the 11-cell matrix, that it covers every backend the CLI advertises AND that the driver script walks exactly it, the tracker blocks, the `!ref:`s, the annotation gate, and that no engine is asked for a metric it cannot produce) — CONFIG-level, since a machine need not carry all eight frameworks — plus `tests/test_restorers.py::test_every_backend_puts_its_metrics_on_the_trackers`, the fleet check the third of these bugs earned. **Verified end to end 2026-08-06 against MLFLOW, on the SEEDED config:** `examples/sweep/run_sweep.sh --tracker mlflow --epochs 5` — **11/11 FINISHED**, every row carrying `val/psnr` + `val/mse` + `val/loss`, ten of eleven carrying the training columns (only `huggingface`, deliberately). **`torch_zoo` 22.1886 dB against `lightning_zoo` 22.1836 — 0.005 dB apart**, a hand-written loop and a `pl.Trainer` producing the same number from the same config, which is the claim this project makes, executed (the smaller network agrees to 0.03: `torch_dncnn` 20.7328 / `lightning_dncnn` 20.7023). **`torch_zoo`'s 22.1886 is the THIRD appearance of that exact figure** — the two seeding probes produced it as well, in a different tracker and a different sweep, which is what the seeding mandate buys. The five `*_dncnn` rows span 20.39-20.73 dB (mlx 20.3854 / keras 20.4558 / tensorflow 20.4879 / jax 20.6757 / lightning 20.7023 / torch 20.7328) — a THIRD of a dB across five frameworks on one 57,635-parameter network, tighter than the unseeded run's half a dB. - **fastai Reports PSNR Through A CONFIGURED ALIAS, Because The Sweep Made Its Absence A HOLE (`FastaiRestorer`, 2026-08-06):** `fastai.metrics` publishes `mse` / `mae` / `rmse` / `msle` and nothing scale-aware, so the quantity the other seven engines report was unreachable by NAME — which was a fine thing to write down while each backend was read alone, and became the single blank cell in the headline column the moment eleven runs were put in one table. `distilaide.fastai_restorer.PeakSignalNoiseRatio` closes it, and it is the SANCTIONED exception rather than a breach of the no-wrappers rule: **it wraps nothing** (there is no upstream fastai metric to wrap) — what it supplies is the ACCUMULATOR, exactly as fastai's own `DiceMulti` does for its quantity, and the ARITHMETIC is `matrainer.metric_functions`' verbatim, shared with the JAX / MLX / HuggingFace loops so the column means one thing in every row. **The accumulation is the whole point:** PSNR is a LOGARITHM of a mean squared error, so an `AvgMetric` over a per-batch value would have been one line and WRONG in a way that moves with the batch size — measured on four ragged batches, accumulating gives 7.796619 (agreeing with `torchmetrics.PeakSignalNoiseRatio` to six decimals and identical whether fed as four batches or one) against 7.771327 for the per-batch mean. Its `name` property is `psnr`, not the class name, because a metric reported under its own class name opens a column no other row fills. **It forced `data_range` onto this backend**, which had been the ONE restorer without it — fastai's own vocabulary is scale-free and never needed one. `_METRIC_ALIASES` is tried BEFORE `fastai.metrics`, since an alias exists precisely where the upstream lookup would fail. The precedent is the per-pixel project's `pixel_accuracy`, and the trigger is identical. SSIM is still absent and still honest: no accumulator would help, because there is no shared implementation to hold.
- **The ZOO Holds LEARNED And CLASSICAL Models In ONE Slot — `DeepInvModel` (2026-08-05):** one wrapper, a closed `RestorationArchitecture` Literal of FOURTEEN entries spanning two kinds: the learned nets (`dncnn` / `drunet` / `scunet` / `swinir` / `restormer` / `ffdnet` / `unet` / `srresnet`) and the classical algorithms (`tv` / `tgv` / `wavelet` / `median` / `bilateral` / `bm3d`), which have **exactly zero parameters** (measured) and wear the `nn.Module` interface anyway. **Putting both behind one `model:` key is the POINT, not a convenience:** `distilaide evaluate` then scores BM3D and a trained DnCNN through the same PSNR/SSIM path, on the same data, into the same tracker — the comparison anyone choosing a denoiser actually wants, and precisely what the predecessor dispatcher could not do because its classical and learned methods were different code paths with no metrics at either end. **A `task: fit` over a parameter-free architecture is REFUSED BY NAME on all three backends**, pointing at `distilaide evaluate`: torch's own failure is *"optimizer got an empty parameter list"*, several frames from the `arch:` line that caused it (fastai's is worse — it surfaces inside `fit_one_cycle`). The refusal is TASK-scoped, never model-scoped: the same object is exactly right for an evaluation, and a run refused by one backend and accepted by another would make the cross-backend comparison a lie. Three facts about the zoo the wrapper encodes rather than restates: (a) **the channel knob has five different names** — `in_channels` (DnCNN/DRUNet/Restormer/UNet), `in_nc` (SCUNet), `in_chans` (SwinIR), `img_channels` (FFDNet), `channels` (EPLL), and none at all on the classical ones — so ONE declared knob is translated by INSPECTING the target's signature (`_build_kwargs`), never by a per-architecture table a deepinv release could outdate; (b) **`sigma` is a MODEL knob** because only the architecture decides whether it matters — `drunet`/`bm3d`/`tv`/`tgv` REQUIRE it (`tv` raises *"Regularization parameter (ths) was not passed"*), `dncnn`/`unet` are blind denoisers that ignore it — and it is passed POSITIONALLY, because the zoo agrees on the argument's POSITION (`Denoiser.forward(x, sigma)`) and not on its name (`TVDenoiser` calls it `ths`); (c) **`pretrained` defaults to `None`, a deliberate DIVERGENCE from deepinv's own `"download"`** — a training project must not silently start from somebody else's weights, nor need the network to build. Lazy-init as every other zoo wrapper: the constructor stores config ONLY, the build is cached in the PUBLIC submodule `self.restorer` (naming it `self.model` would make Lightning's `model.` prefix strip chew through this wrapper's own attribute name), and `solidify()` / `backbone` / `forward()` share the one cache. Pinned in both directions by `tests/test_deepinv_model.py` — every Literal member must resolve to a real `deepinv.models` class, so a rename fails loudly instead of leaving an architecture silently unofferable.
- **A Model Wrapper NAMES The Weights It Loads — `model_refs` (2026-08-05):** `DeepInvModel` exposes a `model_refs` property returning a LIST of `matrainer.uri.ModelRef`, which the tracking layer walks off the configured graph into the run manifest's `models` section — NO consumer calls anything. THREE rules, all load-bearing: (1) **read STORED CONFIG ONLY** — the property is asked of a wrapper that may never run, so it must never build, download or open anything (pinned by `tests/test_model_refs.py`, which asserts the lazy cache is still `None` afterwards); (2) **report an EMPTY list when nothing external was loaded** — which is this project's DEFAULT, since `pretrained` is `None`; (3) use the shared `file_model_ref` helper for a checkpoint rather than formatting a URI by hand. The zoo URI is `deepinv://<arch>?weights=<set>` with **NO `url`**, and that is measured rather than lazy: deepinv routes published weights through THREE different places depending on the architecture — a Hugging Face repo under `deepinv/` for dncnn/drunet/scunet/srresnet/restormer, a GitHub release asset for swinir, and nothing at all for ffdnet (which raises *"has no downloadable weights"* when asked) — so a single repository URL would be wrong for most of the zoo. Same shape of answer as the segmentation project's `smp://`.
- **The SHARED DnCNN SPEC Is A PACKAGE, Apart From The Zoo Wrappers — `distilaide/dncnn/` vs `deepinv_model.py` (2026-08-06):** the two kinds of model here answer different questions and only look alike because both map an image to an image. A **zoo wrapper** exists to reach somebody else's architecture and weights, and its knobs are about the zoo (`arch`, `pretrained`, a checkpoint); it stays at the TOP LEVEL, one `<backend>_model.py` each. A **DnCNN** implements `distilaide/dncnn/spec.py` and wraps NOTHING; its knobs are the architecture itself (`depth` / `width` / `kernel_size` / `seed`), and its whole reason to exist is that the implementations are the SAME network — a claim about the OTHER implementations rather than about its own backend. **It exists because the zoo does not line up:** deepinv is torch-ONLY, so a cross-framework comparison built on it could never include Keras, TensorFlow, Flax or MLX, and five zoo models would compare five networks instead of five frameworks. `spec.py` owns the constants AND **derives** `trainable_parameter_count` (57,635 at the defaults), so each implementation is checked against the CLAIM rather than against whichever was written first — the layer ORDER is prose, because different APIs cannot share code. **Excluding batch norm's running statistics takes a DIFFERENT mechanism in each framework and that is the wrinkle to know:** torch holds them as BUFFERS (`requires_grad` filtering does it), Keras as non-trainable WEIGHTS (`trainable_weights` does it), raw TensorFlow as `trainable=False` variables, Flax as `nnx.BatchStat` (a different variable TYPE in one state tree), and **MLX keeps them in the SAME parameter tree as the weights**, so there the exclusion is a NAME filter — without it the five-way match breaks. **THE RESIDUAL CONNECTION is the architecture's idea and it is parameter-free:** DnCNN predicts the NOISE and subtracts it, which is why approximate identity is its cheapest local optimum and a run's first epoch lands on the do-nothing baseline (see the Current state — it is a TRAINING property, not an init one). Two per-framework facts are load-bearing: **MLX's `valid_parameter_filter` ends in `and not key.startswith("_")`**, so the built network is held in the PUBLIC attribute `net` — as `_model` (its Keras/TF/Flax twins' name) the whole network is filtered out of `parameters()`, the optimizer sees an empty tree, and the loop applies gradients to nothing FOREVER without raising; and **an nnx attribute first assigned `None` becomes STATIC in Flax's pytree**, so the lazy build is wrapped in `nnx.data`. `TorchDnCNN` serves ALL THREE torch backends — they differ in the loop, not in what a model is — which is why there is no `fastai_dncnn.py`. **`distilaide/dncnn/__init__.py` imports NOTHING and that is load-bearing:** the package root resolves every backend name lazily, and an `__init__` re-exporting the implementations would drag in torch AND keras AND tensorflow AND flax AND mlx the moment anything under the package — including the dependency-free `spec.py` — is touched. Unlike a U-Net there is **no size divisor**: DnCNN is fully convolutional and never changes the spatial size, so a raster constraint added here by analogy would be one this architecture does not have (pinned).
- **Every Engine SCALES Its Pair To `[0, 1]` Explicitly — `Scale` In The Torch Chain, `Normalize` Above The Copy In A Channels-Last One (2026-08-06, amended 2026-09-27):** `data_range: 1.0` is only true if both halves of the pair are floats in `[0, 1]`; left as uint8 in `[0, 255]` the run reports **`psnr: -27` and `mse: 548`** (hit for real on the first Keras run). recordstream's `ToTensor` converts HWC→CHW and nothing else, so the scaling is always an op of its own: the torch chain puts `recordstream.ops.numpy.Scale {}` right before its two `ToTensor` steps (no `field`, so it scales both `image` and `target`), and a channels-last chain — which has no `ToTensor` — carries an `albumentations.Normalize` with `std: 1` and `max_pixel_value: 255` ABOVE the copy so BOTH halves inherit it. Every engine then has its targets in `[0, 1]` and one `data_range` is true for all of them. A consequence worth knowing: in the channels-last chain `GaussNoise` runs on FLOAT data, where albumentations reads `std_range` against a max of 1.0 instead of 255 — so the same `[0.1, 0.1]` means the same sigma either way (measured: 0.0992 realised against the torch chain's 0.0993).
- **The KERAS Family Has NO Image Metrics, And The ONE Shim Is The Sanctioned Exception (2026-08-06):** `keras.metrics` ships no PSNR and no SSIM (verified against Keras 3.15 — its regression family is `Mean{Squared,Absolute}Error` and friends). - **A Restoration Metric MUST Be Accumulated Over The SPLIT, Never Averaged Per Batch (2026-08-05):** PSNR is a LOGARITHM of a mean squared error, so the mean of per-batch PSNRs is not the PSNR of the split, and the two answers drift apart as the batches differ from one another. Every backend therefore `update()`s per batch and `compute()`s once at epoch end — `_report_epoch_metrics` (lightning) and `_epoch_metrics` (torch) — which is what keeps two runs at different batch sizes comparable and what makes the lightning and torch columns mean the same thing. Do NOT "simplify" a loop to `fn(preds, target)` averaged over the epoch. Note the ASYMMETRY with the per-pixel and classification tasks: every full-reference image metric is a SCALAR, so there is no vector or matrix to route around `log_dict` and no text/figure channel here — `scalar_metrics` still guards the call, because a config may wire one that is not.
- **The fastai Backend Swaps The LOOP And Nothing Else — And Its Loss Needs NO Axis Fix (2026-08-05):** `FastaiRestorer` runs on torch, so it reuses `DeepInvModel` unchanged, the `[N, C, H, W]` batch shape, `collate_records` and the torch losses — the `fastai` block in the example config overrides `runnable` and `metrics` and nothing else. What it owns is `_to_tuple` (fastai unpacks a batch POSITIONALLY, so the batch must BE a tuple rather than the record dict a `LightningModule` reads by key — and for THIS task both halves are images, so it is two identical `batch_tensor` calls with no dtype to name, the shortest version of that method in the workspace). **The interesting part is a NON-problem its segmentation sibling has:** there, `CrossEntropyLossFlat` must be given `axis=1` because its default flattens the CHANNEL dimension — which carries the CLASSES — into the batch. An image-to-image loss has no class dimension, so flattening a `[N, C, H, W]` pair identically on both sides changes nothing: `L1LossFlat` and `nn.L1Loss` return the SAME value to full precision (measured: 0.3320147693157196 from both), as do `MSELossFlat` and `nn.MSELoss`. - **A FORKED DataLoader Worker Needs Its Source WARMED (2026-08-05):** `import fastai` sets the multiprocessing start method to **`fork`** at import — PROCESS-WIDE, so every backend sharing that interpreter inherits the hazard. A forked child inherits memory but NOT threads, and if it is the first to touch a lazy source the download runs there, reaching `_scproxy` / CoreFoundation on macOS, which is not fork-safe: a **SIGSEGV with no Python traceback**, surfacing only as `DataLoader worker exited unexpectedly`. Do NOT "fix" a recurrence by setting `num_workers: 0` — that avoids the fork rather than the bug, and makes the crash look flaky. - **Task-Shaped Defaults Are SENTINELS:** `loss_fn` (`loss` on fastai) and `metrics` default to **`None`** — meaning *not chosen*, never *no loss*. - **The CORE Is Backend-Free; A Framework Belongs To Its Extra:** `pip install distilaide` gives the CLI and config surface only — `torch` / `torchvision` / `torchmetrics` / `deepinv` / `albumentations` live in `[torch]`, which `[lightning]` and `[fastai]` both build on. **Every backend-owned name in `distilaide/__init__.py` is therefore LAZY (PEP 562)**, mapped to `(module, extra)` so `import distilaide` pulls NO framework and touching a missing one raises an `ImportError` naming the exact extra rather than a traceback from three libraries down. Keep `_BACKEND_NAMES` in step with the extras: a name whose extra does not exist would advertise an install command that fails. **P4 (2026-08-07): the RESOLVER is `matrainer._exports.lazy_exports(__name__, _BACKEND_NAMES)`** — the machinery was identical in every training project's root, so the hand-written `__getattr__`/`__dir__` pair is gone; the `_BACKEND_NAMES` table stays here as project data. `DeepInvModel` and `TorchRestorer` name the SMALLEST extra that supplies them (`torch`, not `lightning`). `distilaide.torch_restoration` stays a module-level torch import ON PURPOSE — on an install without the extra its entry-point import fails and a discovery scan skips it, which is correct. **`bm3d` is its own sub-extra** rather than part of `[torch]`: `deepinv.models.BM3D` imports the package lazily so every other architecture works without it, and the wheel is a heavy native build a run wiring `arch: dncnn` never touches. `wavelet` likewise needs deepinv's own `ptwt` (it says so itself when asked).

- **EVERY Registering Module Gets A `confluid.configurables` Entry Point, And A Test DERIVES The List:** `import distilaide` registers NOTHING (every name is lazy), so discovery runs entirely off the entry-point table — a scanner imports each module named there, and **the import is what executes the `@configurable` decorators**. A module missing from the table registers nothing, and **the failure is silent in every way a developer would notice**: a dotted path in YAML imports the module itself so configs keep working, and `cli.py` imports its own backend so runs keep working — only navigaitor's pickers, the form-specs and the StreamStudio palette go blind, by offering FEWER options. Naming: `distilaide-<backend>` for a runnable, `distilaide-<backend>-model` for a zoo wrapper, `distilaide-<framework>-restoration` for a loss/metric set. Adding a registering module means adding its entry point in the SAME change, then `uv pip install -e ./distilaide --no-deps` for the metadata to take effect. `tests/test_entry_points.py` DERIVES the expectation with an `ast` scan and pins the converse plus the modules-never-`module:attr` rule.
- **No Loss/Metric Wrappers — Register The Upstream Classes, ONE MODULE PER ENGINE:** restoration losses/metrics ARE off-the-shelf upstream classes and they are ENGINE-BOUND, so each engine registers its OWN set from its OWN module with its own entry point: **`distilaide/torch_restoration.py`** (`framework="torch"`) registers `torch.nn`'s `L1Loss` / `MSELoss` / `SmoothL1Loss` / `HuberLoss` as `role="loss"`, and the `torchmetrics.image` FULL-REFERENCE family (`PeakSignalNoiseRatio` / `StructuralSimilarityIndexMeasure` / `MultiScaleStructuralSimilarityIndexMeasure` / `ErrorRelativeGlobalDimensionlessSynthesis` / `RootMeanSquaredErrorUsingSlidingWindow` / `SpectralAngleMapper` / `UniversalImageQualityIndex`) as `role="metric"`. **Every registered class MUST be named in the module's literal `__all__`**: `scan_module` filters by `__module__` (which is `torch` / `torchmetrics` for these), so the `__all__`-gated pass is the ONLY thing carrying them into the StreamStudio palette — `tests/test_categories.py` pins the two lists equal in both directions. Deliberately NOT registered: the no-reference metrics, the distribution metrics, and `LearnedPerceptualImagePatchSimilarity`, which DOWNLOADS a VGG/AlexNet backbone on first use — a metric that silently pulls weights over the network does not belong in a picker's default list (a config can still name it by dotted path).
- **Generic Primitives Live UPSTREAM — distilaide owns NO data plumbing:** the whole degradation pipeline is recordstream's, and image restoration needed exactly ONE primitive added there: **`recordstream.RestorationOutput` + `restoration_output()`** (the prediction contract). Everything else already existed — `ConvertToImage` resizes, `CopyField` makes the clean copy, a bare `albumentations.GaussNoise` degrades the input, `ToTensor` converts both halves, `collate_records` stacks them, `batch_tensor` / `batch_metadata` read them back. Do NOT add a distilaide collate, a distilaide noise op, or a batch reader here. **The contract carries ONE key (`image`) and that is it working, not a stub:** the other tasks emit something that needs interpreting (logits vs probs vs class ids), while an image-to-image model emits the answer — so what a consumer must be told is precisely that the array is a picture in the INPUT's value range, not logits to softmax and not a residual to add back.
- **Discovery Tags (`task` / `role` / `framework`):** distilaide tags its classes `@configurable(task="restoration", role=…, framework="torch")` — `DeepInvModel` is `role="model"` (deriving `category="restoration_model"`), and each merged restorer is `role="trainer"`; its evaluate/test/predict capabilities are the SAME class, declared via its `@entrypoint`-annotated methods, so there is no separate evaluator class and no `role="evaluator"` tag. Preserve the tags when adding or renaming — `tests/test_categories.py` pins them, and a dropped tag silently empties the corresponding picker.
- **`run()` Dispatches Through `run_entrypoint(self, self.task)` — The Markers ARE The Dispatch Table:** do NOT reintroduce a hand-written `{task: method}` dict. It restates the mapping a second time and the copies drift in the direction that bites: navigaitor pins `task:` from `entrypoint_tasks` (the markers), so a capability added to the markers and forgotten in the dict emits a GENERATED config that dies at dispatch while discovery advertises it as supported.
